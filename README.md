# 萌芽（Mengya）母婴健康与育儿内容平台 - 本地传统部署版 (mengya-local)

> **GitHub 仓库地址**：[https://github.com/18227370901/mengya-traditional.git](https://github.com/18227370901/mengya-traditional.git)
> **兄弟项目**：[https://github.com/18227370901/mengya-docker.git](https://github.com/18227370901/mengya-docker.git)


本项目为萌芽（Mengya）平台的**本地传统直接部署工程（mengya-local）**，专为开发者日常本地调试、源码热重载开发以及无 Docker 容器环境的轻量级主机部署量身定制。

---

## 一、架构模型与安全网络拓扑

| 层次/模块 | 运行技术 | 监听地址与端口 | 安全网络边界与说明 |
| :--- | :--- | :--- | :--- |
| **Django 一体化服务** | Python 3.10+ (Django + DRF + React SPA 静态托管) | `0.0.0.0:5173` | **宿主机对外部唯一直达入口**。前端打包产物已合并至 Django 后端，单进程统一托管 SPA 页面、静态资源与后端 API，彻底移除 Node.js 常驻服务，内存开销降低 70% 以上。浏览器访问 `http://localhost:5173/`。 |
| **本地数据** | SQLite3 | `backend/db.sqlite3` | 本地轻量化独立存储，开箱即用，支持自动迁移。 |

> **极简低内存架构说明**：
> 系统采用单体一体化托管模式，无需运行任何 Node.js 常驻服务。前端通过生产构建合并至 Django `templates/` 与 `static/` 目录，全站仅需一个轻量 Python 进程即可完整运行，彻底杜绝服务器内存暴涨与 OOM 隐患。

## 三、快速开始与参数自定义 (./run.sh / sh run.sh)

### 脚本组件化架构与 bin/ 模块化分层治理 (v1.41 重构)
为彻底解决脚本代码量膨胀、功能耦合不易阅读的问题，系统对传统版运维脚本执行了**深度组件化解耦**：`run.sh` 仅保留核心启停控制流程与参数分发，所有专业能力分别下沉至 `bin/` 专属模块库：

```text
mengya-local/
├── run.sh                  # 主运维入口（基础启停流程、参数解析、子命令分发，轻量清爽）
├── run.ps1                 # Windows PowerShell 运维管理脚本
└── bin/                    # 模块化独立函数库
    ├── env.sh              # 基础环境、.env 读写同步、绝对路径规范、域名规约、缓存清理、重启会话注销
    ├── process.sh          # 跨平台端口探针、进程树递归清理、PID 读取管理、多进程协同停止
    ├── python.sh           # Python 解释器侦测、虚拟环境依赖校验 (ensure_backend_deps)
    ├── db.sh               # 硬件感知、3大数据库模式决策向导(严格默认SQLite)、共享PG建库与专属账号
    ├── nginx.sh            # SAN 多域名证书签发、Nginx 反代配置写入、带时间戳快照防误触机制
    └── data.sh             # 种子数据与全量样例初始化 (init_data_local)
```
- **模块加载守卫**：`run.sh` 启动时循环检测装载 `bin/*.sh` 各子模块，缺失即报警退出，保障脚本运行安全性；
- **功能全量守恒**：100% 保持所有命令参数（`-p`, `-u`, `-P`, `-m`, `--shared-pg`, `--reconfig`, `-y` 等）与定时任务免交互逻辑一致。


在 `mengya-local` 根目录下执行：

```bash
# 1. 启动前后端服务（启动前自动清理垃圾与缓存，自动检查并安全配置 SSL 证书与 Nginx 反代）
./run.sh start

# 2. 命令行直传参数自定义启动（自动同步更新至 .env）
./run.sh start -p 5175                         # 自定义前端服务内部端口为 5175
./run.sh start -p 5173 -u superadmin -P Pass123 # 自定义端口与超级管理员账密启动
./run.sh restart -p 5175                       # 重启并变更为 5175 端口

# 3. 查看服务运行状态与端口占用
./run.sh status

# 4. 重启前后端服务（重启前自动清理垃圾与缓存）
./run.sh restart

# 5. 彻底停止前后端服务并释放端口
./run.sh stop

# 6. 生成基于 SNI 443 端口的 Nginx SSL 反向代理配置
./run.sh add_nginx
./run.sh add_nginx -d mengya.myhost.com        # 自定义 SNI 域名反代配置

# 7. 检查并补齐全量样例数据（孕期周历/胎教故事/孕期食谱/幼儿百科/待产清单/商品/品牌）
./run.sh init_data
./run.sh init_data --force                     # 强制全量覆盖重建所有样例数据

# 8. 查看完整帮助信息与可用选项
./run.sh help
```

### 常用命令行自定义参数选项
| 选项 | 长参数 | 默认值 | 作用说明 |
|---|---|---|---|
| `-p` | `--port` | `5173` | 自定义前端内部运行端口（自动持久化写入 `.env` 的 `FRONTEND_PORT`） |
| `-u` | `--admin` | `admin` | 自定义超级管理员账号/手机号（自动持久化写入 `.env` 的 `ADMIN_USERNAME` 与 `ADMIN_PHONE`） |
| `-P` | `--password` | `admin123` | 自定义超级管理员登录密码（自动持久化写入 `.env` 的 `ADMIN_PASSWORD`） |
| `-n` | `--nickname` | `管理员` | 自定义超级管理员前台展示称谓（自动持久化写入 `.env` 的 `ADMIN_NICKNAME`） |
| `-d` | `--domain` | `mengya.local localhost` | 自定义 Nginx 反代 SNI 域名（自动持久化写入 `.env` 的 `SERVER_NAME`） |
| `-m` | `--mode`, `--db-mode` | `sqlite` | 显式指定数据库部署模式（`sqlite` / `shared` / `dedicated`，免交互） |
| - | `--shared-pg` | `pgvector-18` | 指定共享 PostgreSQL 容器名称（共享模式下自动建库与账号） |
| - | `--reconfig` | - | 重新唤起数据库部署模式交互式向导（覆盖 `.env` 记忆） |
| `-y` | `--non-interactive` | - | 全自动免交互模式（自动根据硬件推荐并写入 `.env`，适合脚本/CI） |

### Nginx 反代路径智能绝对化与多域名 SAN 支持
- **权威域名以 `SERVER_NAME` 为准**：通过 `-d / --domain` 自定义 SNI 域名，完整生效至 Nginx 配置中；自动提取首个域名为主域名用于证书 CN，并自动遍历所有域名写入 OpenSSL SAN 扩展列表，多域名访问全兼容。
- **证书路径默认本地化与自动创建**：默认使用当前项目根目录下的 `ssl/` 目录（未显式配置 `NGINX_CERT_DIR` 时自动在当前项目下创建并使用 `ssl` 目录）；无论在 `.env` 或脚本中配置相对路径还是绝对路径，脚本在初始化时均自动规范化为物理绝对路径并自动创建目录，彻底杜绝 Nginx 因相对路径寻找证书失败或外部目录依赖而崩溃。

### 环境配置自动自愈加固
- **配置环境自动自愈**：`run.sh` 启动前检测若无 `.env` 文件，自动从 `.env.example` 模版克隆初始化，避免因配置文件缺失导致环境变量无法解析。

启动完成后，打开浏览器访问：[http://localhost:5173/](http://localhost:5173/)

## 四、管理员账号管理规范

系统在启动时自动调用 `ensure_admin` 流程，贯彻**单一管理员生命周期保障**机制：

1. **默认凭证**：
   - 管理员账号：`admin`
   - 管理员密码：`admin123`
   - 管理员昵称：`管理员`
2. **自定义配置**：
   在根目录 `.env` 文件中配置以下变量即可自如替换管理员凭据：
   ```bash
   ADMIN_USERNAME=your_admin
   ADMIN_PASSWORD=your_strong_password
   ADMIN_NICKNAME=超级管理员
   ```
3. **单管理员保障**：
   - 每次服务启动时，系统自动确保只有 `ADMIN_USERNAME` 指定的账号具备管理员权限。
   - 自动清理历史残留的其他管理员账号，避免混淆。
   - **普通用户保护**：严格只清理历史管理员账号，系统内的所有普通注册用户数据完整保留，绝不误伤。

## 六、常见问题排查

1. **为什么直接打开 `http://localhost:5173/api/` 会提示未提供认证信息？**
   - 这是符合预期的安全机制。后端已保护在回环网络中，且需携带前端登录凭据（JWT Token）。请始终通过前端入口 [http://localhost:5173/](http://localhost:5173/) 进行正常访问与登录。
2. **停止服务时提示端口被外部进程占用？**
   - 执行 `./run.sh stop`，脚本会自动检测 PID 文件、监听端口及匹配进程树，进行平滑关闭并兜底强制释放端口。

## 八、多数据库部署模式自适应架构与双版本物理隔离规范 (v1.40)

为彻底保障传统版与 Docker 版的数据独立性，并为运维提供灵活的数据库选型能力，传统版本在保持默认本地独立 SQLite 的基础上，全面支持**多数据库部署模式自适应架构与智能向导**：

### 1. 三大数据库部署模式深度支持
| 部署模式 | 标识 (`DB_MODE`) | 架构特征 | 适用场景与资源消耗 |
| :--- | :--- | :--- | :--- |
| **SQLite 本地化单文件 (默认推荐)** | `sqlite` | 严格采用宿主机本地 `mengya-local/db.sqlite3`，由一体化 Python 进程直接读写，**零额外 PG 容器** | 传统版严格默认推荐，超低配轻量运行，整站常驻约 **50MB**，与 Docker 版数据 **100% 物理硬隔离** |
| **共享已有 PostgreSQL 实例** | `shared` | 共用宿主机已在运行的 PG 容器（如 `pgvector-18`），通过管理接口自动幂等创建应用专属库（`mengya_local`）与账号（`mengya_local`），**零多余容器** | 宿主机已有 PG 运行，最大化复用已有基础设施，节省 **80MB+** 重复容器开销 |
| **独立专属 PostgreSQL 容器** | `dedicated` | 专属容器 `${APP_NAME:-mengya_local}-pg`，宿主机端口映射 5433（防 5432 冲突），**严格复用本地镜像** | 宿主机需要独立 PG 服务实例，独占专有数据库 |

### 2. 传统版本严格默认 SQLite 与数据隔离机制
- **默认存储引擎固化**：传统版核心配置 `config/settings.py` 严格固化使用**本地独立单文件 SQLite**（`db.sqlite3`），切断上级目录跨工程环境变量污染，默认忽略外部残留的 `DATABASE_URL`，开箱即用，零外部数据库依赖；
- **共享 PG 实例下的库名隔离**：若用户显式选择 Mode 2 共享宿主机已有的 PG 容器，传统版创建并使用的数据库名为 `mengya_local`，专属账号为 `mengya_local`，而 Docker 版使用 `mengya_docker` 专属数据库与专属账号 `mengya_docker`，在逻辑库和权限层面形成物理隔离，彻底杜绝数据交叉污染；
- **用户体系与业务数据独立**：两套版本各自拥有独立的用户表、AI 配置与业务记录，无论如何部署均互不影响。

### 3. 本地镜像就地严格复用与 PG15 默认锁定机制
- **内置默认轻量成熟镜像**：独立专属 PostgreSQL 模式默认标准镜像锁定为 `postgres:15-alpine`（整站镜像约 80MB，常驻内存仅 ~25MB）；
- **探针解耦与扫描优先级**：彻底移除对宿主机其他无关运行容器的越界探测，本地扫描优先匹配：① 本地已有的 `postgres:15-alpine`；② 本地兼容的官方 PG15 镜像 (`postgres:15*`)；③ 本地官方轻量 alpine 镜像 (`postgres:*alpine`)；④ 兜底选用 `postgres:15-alpine` 并在本地不存在时按需下载 (`pull_policy: if_not_present`)；
- **配置自动纠偏**：默认模式下不向 `.env` 写入 `DB_IMAGE`（保持空值跟随默认），若检测到 `.env` 残留历史误判的 `pg18` 或 `pgvector` 镜像，启动时自动纠偏清除；
- **专属容器与存储卷自愈**：启动时检测已有容器镜像，若镜像不匹配自动停止并删除旧容器以便以新镜像重新创建；若检测到历史遗留 PG18 数据卷，自动重置确保 PG15 正常初始化。

### 4. 定时任务 / Cron / 重启全静默免交互保护机制
- **重启与运维命令天然免交互**：执行 `./run.sh restart`（或 PowerShell `.\run.ps1 restart`）、`stop`、`status` 等命令时，系统天然跳过向导交互，直接沿用已有配置；
- **配置持久化记忆**：首发部署交互完成后，配置自动持久化写入 `.env` 中的 `DB_MODE`、`USE_POSTGRES`、`DATABASE_URL` 等变量，后续启动直接读取；
- **无 TTY / 定时任务自愈**：在 Cron、Systemd、CI/CD 等非交互环境（`[ ! -t 0 ]` 或 `-y`）中，向导自动采用推荐配置（传统版严格推荐 SQLite）并自愈写入 `.env`，彻底消除阻塞；
- **显式重配入口**：运维人员如需变更已配置的数据库模式，支持显式追加 `--reconfig`（例如 `./run.sh start --reconfig`），随时重开交互式决策。

为彻底保障传统版与 Docker 版的数据独立性，系统建立了双版本底层数据库的 **100% 物理硬隔离机制**：

1. **默认存储引擎固化**：
   - 传统版（`mengya-local`）核心配置 `config/settings.py` 严格固化使用**本地独立单文件 SQLite**（`mengya-local/db.sqlite3`）；
   - 彻底切断上级目录 `.env` 环境变量跨工程污染，默认忽略外部残留的 `DATABASE_URL`，开箱即用，零外部数据库依赖。
2. **外部 PostgreSQL 按需显式启用**：
   - 仅当管理员主动在本地 `.env` 中显式声明 `USE_POSTGRES=True` 且配置了有效连通的 `DATABASE_URL` 时，传统版才会尝试切换连接外部 PostgreSQL。
3. **与 Docker 版完全物理隔离**：
   - Docker 版（`mengya-docker`）数据库运行于独立容器 `mengya_docker-pg`，持久化于 Docker 命名存储卷 `mengya_docker_pgdata`，内部端口 5432 仅供容器内网互联，不对宿主机暴露；
   - 传统版在宿主机本地严格读写 `db.sqlite3` 文件，两者在数据存储介质、物理路径与网络边界上均实现全方位物理隔离，彻底杜绝数据交叉污染。

### 6. .env 环境变量持久化与数据库存储方式重新选择操作说明 (v1.43)

#### 6.1 能否直接删除或清空 .env 文件？
- **结论**：**不建议直接删除或清空 `.env` 文件！**
- **深度原因**：
  `.env` 文件是全系统的持久化配置核心，不仅存储数据库模式 (`DB_MODE`)，还锁定了系统通信安全密钥 (`SECRET_KEY`)、自定义访问端口 (`FRONTEND_PORT`)、超级管理员账号与初始密码 (`ADMIN_USERNAME` / `ADMIN_PASSWORD`) 以及 SNI 域名 (`SERVER_NAME`) 等关键状态。
  若直接删除或清空 `.env`，虽然下次启动确实会触发数据库模式选择，但会导致系统密钥与自定义端口被全量重置，造成历史会话失效、端口冲突或账密被重置。

#### 6.2 重新选择数据库模式的 3 大标准方式
1. **方式一：命令行原生重配入口（强烈推荐，安全且零副作用）**
   - **交互式向导重新选择**：
     ```bash
     ./run.sh reconfig
     # 或
     ./run.sh start --reconfig
     ```
     *原理*：强制唤醒硬件感知探针与交互选择菜单，重新选择 SQLite / 共享 PG / 独立 PG 模式，同时完整保留 `.env` 中的端口、密钥与业务参数。
   - **单行命令显式切模（免去交互）**：
     ```bash
     ./run.sh start -m sqlite       # 切换为 SQLite 本地单文件模式
     ./run.sh start -m shared       # 切换为共享宿主机已有 PG 模式
     ./run.sh start -m dedicated    # 切换为独立专属 PG 容器模式
     ```
     *原理*：直接以命令行指定目标模式启动，底层自动更新并持久化至 `.env`。

2. **方式二：精准修改或剔除 .env 中的 DB_MODE 变量**
   - 直接编辑 `.env` 文件，将 `DB_MODE=...` 改为目标值（例如 `DB_MODE=shared`）；
   - 或者仅删除/注释掉 `DB_MODE` 这一行（例如 `# DB_MODE=...`）。下次执行 `./run.sh start` 时，脚本感知到未配置模式，将自动重新弹出交互式选择向导，其他变量不受任何影响。

3. **方式三：直接删除/清空 .env 文件的影响**
   - 若执行了 `rm -f .env` 或清空 `.env`，下次执行 `./run.sh start` 时，系统会自动从 `.env.example` 重新全量初始化环境并唤醒选择向导。请仅在需要彻底重置项目环境时使用此方式。

#### 6.3 帮助模块与说明函数 (show_db_reconfig_guide)
- 在 `bin/db.sh` 中封装了专用的说明函数 `show_db_reconfig_guide()`；
- 在执行 `./run.sh help`、`./run.sh -h` 或直接运行 `./run.sh` 时，系统在输出基础命令帮助的同时，会自动调用该说明函数，以高亮框完整展示重新选择操作说明与参数用法，方便初次使用的用户随时查阅。

### 7. PostgreSQL 镜像动态探针感知与零硬编码复用规范 (v1.44)

#### 7.1 镜像决策与复用三级阶梯
1. **用户自定义显式指定（最高优先级）**：
   - 允许通过命令行 `./run.sh start --db-image <IMAGE>` 或在 `.env` 中配置 `DB_IMAGE` 自由指定所需 PG 版本（如 `postgres:15-alpine`, `postgres:16`, `pgvector/pgvector:pg18` 等）；
   - **绝对遵从**：若本地已存在该镜像直接就地复用（`pull_policy: never`）；若本地尚未下载则启动时精准下载该指定版本（`pull_policy: if_not_present`），严禁被本地其他旧镜像覆盖篡改。
2. **宿主机已有镜像优先就地复用（未显式指定时）**：
   - 自动扫描宿主机正在运行的 PG 容器镜像；
   - 扫描本地已有镜像列表（支持各类官方 Alpine 与 PostgreSQL 镜像），直接就地复用匹配镜像，杜绝不必要的网络拉取。
3. **内置默认轻量镜像兜底（本地无任何 PG 镜像时）**：
   - 宿主机本地彻底没有任何可用 PG 镜像时，才自动下载内置轻量成熟镜像（`postgres:15-alpine`，整站镜像仅约 80MB，常驻内存仅 ~25MB），避免盲目下载体积庞大的专用向量镜像。

#### 7.2 共享 PG 模式（shared）零硬编码
- 彻底剔除历史兜底的 `pgvector-18` 硬编码容器名；
- 优先支持用户通过 `--shared-pg <容器名>` 或 `SHARED_PG_CONTAINER` 显式指定；
- 未指定时自动扫描宿主机运行中 PG 容器；若宿主机未检测到可用 PG 容器，给出清晰诊断并自动平滑降级为独立 PG / SQLite 模式，杜绝进程因盲连不存在容器而崩溃。

## 18. 孕周输入自动填充修复与孕x周x天双输入修改（v1.58）
