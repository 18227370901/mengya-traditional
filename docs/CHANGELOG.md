## 2026-10-28 最新更新说明（v1.88.6 版本）： 权限模板快照固化——管理员修改全局默认模板不再自动覆盖已有用户

1. **权限模板「自动同步」缺陷根治**：
   - **痛点与根因**：v1.88.5 及之前权限解析在运行时实时叠加全局默认权限模板（`SystemSetting.default_user_permissions`），管理员修改模板保存后，所有权限快照为空的用户（种子数据用户、被点过「重置为系统默认」的用户）权限立即全量变化，出现「所有用户的权限全部变更为一样」的问题；
   - **语义反转修复**：原「重置为系统默认」按钮直接清空 `custom_permissions`，实际是让该用户永久实时跟随模板（越重置越扩散）；v1.88.6 重定义为一次性固化「最新模板 + 该用户当前宝宝阶段」，与产品预期完全一致。

2. **快照固化模式核心变更**：
   - 新增 `build_initial_permissions()` 统一构建「代码基线 + 最新全局模板 + 宝宝阶段自适应」初始权限快照，模板仅作为快照源，只在**新用户注册**与**管理员点击「重置为系统默认」**两个时机固化落库；
   - `get_user_permissions()` 彻底移除模板实时覆盖段，存量用户（注册固化、迁移固化、管理员定制三类快照）权限此后完全不受模板修改影响；
   - 新注册用户初始权限改为「注册时最新模板 + 宝宝阶段」，此后管理员修改模板同样不影响该用户；
   - 用户切换宝宝阶段（孕期 ↔ 已出生）时，未定制用户仅基于自身快照调整 4 个阶段菜单键（时间轴/食谱/胎教故事/幼儿百科），其余键原样保留；管理员单独定制过的用户完全静态。

3. **存量数据迁移与前端体验增强**：
   - 新增数据迁移 `0035_permission_snapshot`：为存量空快照普通用户固化"当前实际生效权限"，升级前后权限零感知变化；
   - 用户列表与权限弹窗徽标改由后端 `has_custom` 字段（基于 `_admin_customized` 标记）驱动，不再以快照是否为空误判「已定制」；
   - 全局模板 Tab 说明与保存提示明确「仅应用于之后新注册用户，已有用户需在其权限弹窗手动点击重置才更新」；重置确认弹窗强化「用最新模板覆盖该用户现有全部权限、此操作不可撤销」警示文案。

4. **验证结果**：API 端到端 19 项、阶段切换真实 API 11 项、浏览器端到端（列表标签/模板说明/保存提示/重置弹窗）逐项验证全部通过；全部测试数据精确还原（模板原值、用户快照、临时测试用户）；传统版与 Docker 版同步发布，源文件与静态产物 MD5 一致。

## 2026-10-24 最新更新说明（v1.87 版本）： 全员登录会话无操作超时引擎重构与模式 A（覆盖全平台所有登录账号）落地

1. **登录会话无操作空闲超时检测引擎重构与失效缺陷彻底根治**：
   - **痛点与根因**：原 `frontend/src/api/client.ts` 在全局 Axios 请求拦截器中粗暴执行 `localStorage.setItem("mengya_last_active", String(Date.now()))`，导致后台静默轮询（如 `RequireAuth.tsx` 中每 60 秒触发的 `fetchMe()` 权限与用户信息静默同步请求）持续刷新活跃时间戳。空闲时间（`idleMs`）永远被截断在 60 秒以内，导致管理员在风控面板设定的任何分钟级超时（如 15、30 分钟）永远无法触发；且切回窗口（Focus/VisibilityChange）时先触发请求刷新，导致历史空闲时间被意外冲刷。
   - **架构解耦与精准修复**：
     - 从 Axios 全局请求拦截器中彻底剥离对 `mengya_last_active` 的盲目更新，空闲时间记录专职交由真实的物理人机交互事件（`mousedown, mousemove, keydown, scroll, touchstart, click`）按 3 秒节流写入；
     - 在 `RequireAuth.tsx` 提取统一的 `checkIdleTimeout()` 判定中枢，在路由切换、窗口聚焦与页面可见性恢复时**优先**进行超时判定；一旦空闲时间达到设定阈值，立即熔断后续一切后台请求，执行 `logout()` 并带参跳转 `/login?timeout=1`；
     - 轮询检查周期由 10 秒提升至 5 秒，并接入 `storage` 事件监听，实现多标签页（Tab）跨窗口人机交互状态无缝互通。

2. **采用模式 A 全量扩容：覆盖全平台所有登录账号（普通用户与特权管理员通用）**：
   - 将无操作超时保护机制由单一特权管理账号（`user.is_staff == true`）全面扩展为全平台所有登录账号（普通注册用户与管理员一视同仁）；
   - 更新「用户与权限管控中心」风控面板文案与提示语（「登录会话无操作超时（分钟，全员通用）」），明确说明 0 为禁用，默认推荐 30 分钟；
   - 同步后端数据模型 `SystemSetting.admin_session_timeout_minutes` 字段定义与迁移（`0032_alter_systemsetting_admin_session_timeout_minutes`），保持全局安全基线策略向前兼容。

3. **现场阻断式超时强提醒模态框（Modal）与切回窗口交互防御落地**：
   - **现场全屏遮罩强提示**：当连续空闲达到设定时长，系统不再仅做隐蔽的后台登出，而是在当前界面即刻弹出全屏高优先级阻断模态框（「登录会话已超时」），明确展示超时时长与注销原因，并提供「重新登录」按钮，彻底解决用户等待时无感知无提示的困扰；
   - **人机交互事件前置防线**：在 `mousedown, keydown` 等事件触发时，优先调用 `checkIsTimedOut()`；若已超时则坚决拒绝刷新 `mengya_last_active`，直接唤起超时提示，彻底攻克切回浏览器标签页时点击事件先于校验执行、导致超时被抹平的隐蔽竞态缺陷；
   - **登录页提示状态双保险**：在 `LoginPage.tsx` 增加 `sessionStorage` 状态感知，彻底根除因路由跳转重叠导致 URL `?timeout=1` 参数被冲刷失效的缺陷；
   - **1 分钟测试预设按钮**：在后台安全风控面板新增「1分(测试)」快捷按钮，极大提升功能验收与安全审计效率。

   - **默认配置硬化**：将 config/settings.py 中的默认 DJANGO_DEBUG 调整为 False，同时同步更新 .env 与 .env.example，避免未配置环境变量时落入 Debug 陷阱；
   - **运行时 GC 垃圾回收优化**：在 config/wsgi.py 与启动链路显式执行垃圾回收，降低多线程与高并发请求下的内存碎片占用。

## 八、多数据库部署模式自适应架构与双版本物理隔离规范 (v1.40)

为彻底保障传统版与 Docker 版的数据独立性，并为运维提供灵活的数据库选型能力，传统版本在保持默认本地独立 SQLite 的基础上，全面支持**多数据库部署模式自适应架构与智能向导**：

### 1. 三大数据库部署模式深度支持
| 部署模式 | 标识 (`DB_MODE`) | 架构特征 | 适用场景与资源消耗 |
| :--- | :--- | :--- | :--- |
| **SQLite 本地化单文件 (默认推荐)** | `sqlite` | 严格采用宿主机本地 `mengya-local/db.sqlite3`，由一体化 Python 进程直接读写，**零额外 PG 容器** | 传统版严格默认推荐，超低配轻量运行，整站常驻约 **50MB**，与 Docker 版数据 **100% 物理硬隔离** |
| **共享已有 PostgreSQL 实例** | `shared` | 共用宿主机已在运行的 PG 容器（如 `pgvector-18`），通过管理接口自动幂等创建应用专属库（`mengya_local`）与账号（`mengya_local`），**零多余容器** | 宿主机已有 PG 运行，最大化复用已有基础设施，节省 **80MB+** 重复容器开销 |
| **独立专属 PostgreSQL 容器** | `dedicated` | 专属容器 `${APP_NAME:-mengya_local}-pg`，宿主机端口映射 5433（防 5432 冲突），**严格复用本地镜像** | 宿主机需要独立 PG 服务实例，独占专有数据库 |

### 2. 传统版本严格默认 SQLite 与数据隔离机制
- **默认存储引擎固化**：传统版核心配置 `config/settings.py` 严格固化使用**本地独立单文件 SQLite**（`db.sqlite3`），切断上级目录跨工程环境变量污染，默认忽略外部残留的 `DATABASE_URL`，开箱即用，零外部数据库依赖；
- **共享 PG 实例下的库名隔离**：若用户显式选择 Mode 2 共享宿主机已有的 PG 容器，传统版创建并使用的数据库名为 `mengya_local`，专属账号为 `mengya_local`，而 Docker 版使用 `mengya_docker` 专属数据库与专属账号 `mengya_docker`，在逻辑库和权限层面形成物理隔离，彻底杜绝数据交叉污染；
- **用户体系与业务数据独立**：两套版本各自拥有独立的用户表、AI 配置与业务记录，无论如何部署均互不影响。

### 3. 本地镜像就地严格复用与 PG15 默认锁定机制
- **内置默认轻量成熟镜像**：独立专属 PostgreSQL 模式默认标准镜像锁定为 `postgres:15-alpine`（整站镜像约 80MB，常驻内存仅 ~25MB）；
- **探针解耦与扫描优先级**：彻底移除对宿主机其他无关运行容器的越界探测，本地扫描优先匹配：① 本地已有的 `postgres:15-alpine`；② 本地兼容的官方 PG15 镜像 (`postgres:15*`)；③ 本地官方轻量 alpine 镜像 (`postgres:*alpine`)；④ 兜底选用 `postgres:15-alpine` 并在本地不存在时按需下载 (`pull_policy: if_not_present`)；
- **配置自动纠偏**：默认模式下不向 `.env` 写入 `DB_IMAGE`（保持空值跟随默认），若检测到 `.env` 残留历史误判的 `pg18` 或 `pgvector` 镜像，启动时自动纠偏清除；
- **专属容器与存储卷自愈**：启动时检测已有容器镜像，若镜像不匹配自动停止并删除旧容器以便以新镜像重新创建；若检测到历史遗留 PG18 数据卷，自动重置确保 PG15 正常初始化。

### 4. 定时任务 / Cron / 重启全静默免交互保护机制
- **重启与运维命令天然免交互**：执行 `./run.sh restart`（或 PowerShell `.\run.ps1 restart`）、`stop`、`status` 等命令时，系统天然跳过向导交互，直接沿用已有配置；
- **配置持久化记忆**：首发部署交互完成后，配置自动持久化写入 `.env` 中的 `DB_MODE`、`USE_POSTGRES`、`DATABASE_URL` 等变量，后续启动直接读取；
- **无 TTY / 定时任务自愈**：在 Cron、Systemd、CI/CD 等非交互环境（`[ ! -t 0 ]` 或 `-y`）中，向导自动采用推荐配置（传统版严格推荐 SQLite）并自愈写入 `.env`，彻底消除阻塞；
- **显式重配入口**：运维人员如需变更已配置的数据库模式，支持显式追加 `--reconfig`（例如 `./run.sh start --reconfig`），随时重开交互式决策。

为彻底保障传统版与 Docker 版的数据独立性，系统建立了双版本底层数据库的 **100% 物理硬隔离机制**：

1. **默认存储引擎固化**：
   - 传统版（`mengya-local`）核心配置 `config/settings.py` 严格固化使用**本地独立单文件 SQLite**（`mengya-local/db.sqlite3`）；
   - 彻底切断上级目录 `.env` 环境变量跨工程污染，默认忽略外部残留的 `DATABASE_URL`，开箱即用，零外部数据库依赖。
2. **外部 PostgreSQL 按需显式启用**：
   - 仅当管理员主动在本地 `.env` 中显式声明 `USE_POSTGRES=True` 且配置了有效连通的 `DATABASE_URL` 时，传统版才会尝试切换连接外部 PostgreSQL。
3. **与 Docker 版完全物理隔离**：
   - Docker 版（`mengya-docker`）数据库运行于独立容器 `mengya_docker-pg`，持久化于 Docker 命名存储卷 `mengya_docker_pgdata`，内部端口 5432 仅供容器内网互联，不对宿主机暴露；
   - 传统版在宿主机本地严格读写 `db.sqlite3` 文件，两者在数据存储介质、物理路径与网络边界上均实现全方位物理隔离，彻底杜绝数据交叉污染。

### 6. .env 环境变量持久化与数据库存储方式重新选择操作说明 (v1.43)

#### 6.1 能否直接删除或清空 .env 文件？
- **结论**：**不建议直接删除或清空 `.env` 文件！**
- **深度原因**：
  `.env` 文件是全系统的持久化配置核心，不仅存储数据库模式 (`DB_MODE`)，还锁定了系统通信安全密钥 (`SECRET_KEY`)、自定义访问端口 (`FRONTEND_PORT`)、超级管理员账号与初始密码 (`ADMIN_USERNAME` / `ADMIN_PASSWORD`) 以及 SNI 域名 (`SERVER_NAME`) 等关键状态。
  若直接删除或清空 `.env`，虽然下次启动确实会触发数据库模式选择，但会导致系统密钥与自定义端口被全量重置，造成历史会话失效、端口冲突或账密被重置。

#### 6.2 重新选择数据库模式的 3 大标准方式
1. **方式一：命令行原生重配入口（强烈推荐，安全且零副作用）**
   - **交互式向导重新选择**：
     ```bash
     ./run.sh reconfig
     # 或
     ./run.sh start --reconfig
     ```
     *原理*：强制唤醒硬件感知探针与交互选择菜单，重新选择 SQLite / 共享 PG / 独立 PG 模式，同时完整保留 `.env` 中的端口、密钥与业务参数。
   - **单行命令显式切模（免去交互）**：
     ```bash
     ./run.sh start -m sqlite       # 切换为 SQLite 本地单文件模式
     ./run.sh start -m shared       # 切换为共享宿主机已有 PG 模式

     ```
     *原理*：直接以命令行指定目标模式启动，底层自动更新并持久化至 `.env`。

### 7. PostgreSQL 镜像动态探针感知与零硬编码复用规范 (v1.44)

#### 7.1 镜像决策与复用三级阶梯
1. **用户自定义显式指定（最高优先级）**：
   - 允许通过命令行 `./run.sh start --db-image <IMAGE>` 或在 `.env` 中配置 `DB_IMAGE` 自由指定所需 PG 版本（如 `postgres:15-alpine`, `postgres:16`, `pgvector/pgvector:pg18` 等）；
   - **绝对遵从**：若本地已存在该镜像直接就地复用（`pull_policy: never`）；若本地尚未下载则启动时精准下载该指定版本（`pull_policy: if_not_present`），严禁被本地其他旧镜像覆盖篡改。
2. **宿主机已有镜像优先就地复用（未显式指定时）**：
   - 自动扫描宿主机正在运行的 PG 容器镜像；
   - 扫描本地已有镜像列表（支持各类官方 Alpine 与 PostgreSQL 镜像），直接就地复用匹配镜像，杜绝不必要的网络拉取。
3. **内置默认轻量镜像兜底（本地无任何 PG 镜像时）**：
   - 宿主机本地彻底没有任何可用 PG 镜像时，才自动下载内置轻量成熟镜像（`postgres:15-alpine`，整站镜像仅约 80MB，常驻内存仅 ~25MB），避免盲目下载体积庞大的专用向量镜像。

#### 7.2 共享 PG 模式（shared）零硬编码
- 彻底剔除历史兜底的 `pgvector-18` 硬编码容器名；
- 优先支持用户通过 `--shared-pg <容器名>` 或 `SHARED_PG_CONTAINER` 显式指定；
- 未指定时自动扫描宿主机运行中 PG 容器；若宿主机未检测到可用 PG 容器，给出清晰诊断并自动平滑降级为独立 PG / SQLite 模式，杜绝进程因盲连不存在容器而崩溃。

### 8. 数据库全参连接信息自定义与 --reconfig 交互向导修复规范 (v1.45)

#### 8.1 --reconfig 交互式向导唤起机制
- **直接执行重配**：支持运行 `./run.sh --reconfig` 或 `./run.sh reconfig`，无需前置启动命令，直接唤起硬件感知与部署模式交互菜单；

#### 8.2 数据库连接全参数自定义支持（自动持久化至 .env）
系统支持在命令行直接传递数据库详细连接参数，既有默认值，又支持自定义覆盖：
| 命令行选项 | 对应环境变量 | 默认值（传统版） | 说明 |
| :--- | :--- | :--- | :--- |
| `--db-user <USER>` | `POSTGRES_USER` | `mengya_local` | 自定义 PostgreSQL 用户名 |
| `--db-pass <PASS>` | `POSTGRES_PASSWORD` | `mengya123` | 自定义 PostgreSQL 连接密码 |


## 16. 健康数据严谨性与列表管理增强 · 工程瘦身 · 临床赋能（v1.57）

### 16.1 数据合理性校验（同日唯一 + 覆盖更新 + 未来日期拦截）
- **同日唯一原则**：测量类记录（妈妈 `prenatal_exam` / 宝宝 `growth_measurement`）同一用户同一日期只保留一条——两条录入链路（打卡弹窗 / 深度 BMI 表单）后端统一查重，命中返回 **409 + 当日已有数据摘要**（体重/身高/阶段）；
- **覆盖弹窗**：前端捕获 409 后弹出确认（打卡弹窗内联琥珀色确认条 / 深度表单 ConfirmDialog），用户确认后携 `overwrite=true` 重发，后端**原地更新当日记录**（保留记录 id 与归档时间，不产生重复数据）；妈妈链路覆盖后自动重新生成评估报告，宝宝链路直接 PATCH 原记录；
- **未来日期硬拦截**：所有健康记录（打卡/测量/疫苗）`record_date` 不能晚于今天（serializer 层校验 400 + 前端 date input `max=今天` 双重防线），杜绝时序图与孕周引擎被未来数据污染；
- **疫苗不查重**：同日可接种多剂（乙肝+卡介苗同天），`vaccination` 类型豁免同日唯一约束；
- **宝宝数值软提示**：身高 30~140 / 体重 0.5~40 / 头围 25~60 之外的录入仅作**黄色警示提示，不限制输入**（满足特殊医学场景自由录入需求）。

### 16.2 列表管理（勾选批量删除 + 分页，四处列表全覆盖）
- 四处数据列表统一接入：**妈妈 Tab 测量打卡历史表**、**妈妈打卡明细卡片流**、**宝宝 Tab 测量记录表**、**疫苗 Tab 全部接种记录区**（新增区块）；

## 18. 孕周输入自动填充修复与孕x周x天双输入修改（v1.58）

### 18.1 问题与根因（自动填充失效）
- **问题**：v1.57.1 里孕周输入框只显示 placeholder「自动推算」却无数值填充，用户仍需手填；且仅有整周输入，无法修改推算出的周内天数；
- **根因**：自动填充依赖 `useEffect`（依赖 `gestation?.week`）setState 回填输入框——「推算值未变化不触发 effect」「弹窗打开重置与填充执行顺序竞争」「锚点异步加载时序」多重竞态叠加，导致输入框常为空。

### 18.2 派生显示值方案（两条录入链路同构改造）
- **模型转换**：彻底删除「effect 回填」模式，改为 **touched 标记 + 派生显示值**——`weekDisplay = !weekTouched && gestation ? String(gestation.week) : manualWeek`，未手动编辑时输入框直接绑定推算值（自动填充绝对可靠、无时序依赖），用户 onChange 即置 touched、此后绑定用户值；`useEffect` 职责收缩为「日期/模式变化时重置 touched 回到自动推算」，不再承担填充职责；
- **孕x周x天双输入框**：打卡弹窗与深度 BMI 表单孕周块统一为「[周] 周 [天] 天」双输入框（周 1~42 必填、天 0~6），placeholder「自动推算」/「天」；提示行显示推算依据（档案预产期 / 首次打卡锚点），周与天均可手改（周数偏差 ±1 周内，超差后端 400 拦截）；

## 22. v1.62 首页定时轮询抖动根除与时序看板图表生命周期完整联动

### 22.1 优化背景
1. **首页每隔 15 秒自动闪烁抖动**：`RequireAuth` 中设置了 15 秒间隔的 `fetchMe()` 全局权限同步轮询。接口返回的 `data.stage` 对象字面量每次产生新引用，触发 `HomePage` 中监听 `[stage]` 的 `fetchHomeData()`；而 `fetchHomeData()` 内部第一行执行 `setLoading(true)`，触发 `if (loading) return <div>加载中…</div>` 硬性拦截，导致整页卡片 DOM 瞬间被销毁并替换为占位符，200ms 后再全量重建，视觉上表现为每 15 秒剧烈“抖动/白屏塌陷”。
2. **妈妈孕产档案时序看板新增数据空白**：空数据或初始状态下，`BmiTimeSeriesBoard` 依据自适应规则收拢，JSX 条件渲染未将 `<div ref={chartRef} />` 挂载至 DOM；组件 Mount 阶段的单次 `useEffect([], ...)` 获取 `chartRef.current` 为 `null`，导致 `echarts.init()` 被跳过、图表实例永久处于 `null`；用户后续新增数据或打卡后，尽管纯 React 编写的测量历史表格正常渲染，但图表更新副作用因实例缺失直接退出，导致时序图表看板持续显示空白。

### 22.2 核心改造清单
1. **首页静默无感更新与引用抖动阻断 (`HomePage.tsx` & `authStore.ts`)**：

## 33. v1.73 外部接口服务配置统一管理（天气/节假日/AI公网搜索引擎管线）

### 33.1 背景与目标
系统各模块长期内置默认外部服务地址（Open-Meteo 三接口、timor.tech 节假日、AI 公网搜索引擎管线），
地址、超时、启停、故障转移顺序全部硬编码在代码中，管理员无法在页面上调整。本版本将此类「内置默认调用地址」
统一收口到管理员「外部接口配置」页，实现**多端点、可开关、可排序、自动故障转移、可配置重试参数、一键测试**的运维能力。

### 33.2 覆盖范围（5 个配置组）

| 配置组 | 默认端点 | 说明 |
| :--- | :--- | :--- |
| 天气·地理编码 | `https://geocoding-api.open-meteo.com/v1/search` | Open-Meteo Geocoding |
| 天气·天气预报 | `https://api.open-meteo.com/v1/forecast` | Open-Meteo Forecast |
| 天气·空气质量 | `https://air-quality-api.open-meteo.com/v1/air-quality` | Open-Meteo Air Quality |
| 法定节假日 | `https://timor.tech/api/holiday/year/` | 年份占位符自动补全 |
| AI 公网搜索引擎管线 | DuckDuckGo / Google / Bing / 360 / 搜狗 / 百度 / 雅虎 7 引擎 | 行级地址+行级超时+行级开关+顺序 |

> SearXNG 私有实例地址（`SEARXNG_BASE_URL` 等）仍在「AI 助手配置 → 搜索引擎配置」弹窗维护，
> AI 助手实时检索始终 **SearXNG 优先**，本页公网引擎管线作为其兜底（受 `AI_SEARCH_FALLBACK_ENABLED` 总开关控制）。

### 33.3 核心能力（逐项对照需求）

1. **多端点/多引擎**：每组支持多个端点（天气组/节假日组）或引擎行（搜索管线组），可增删；
2. **行级开关**：每行独立「启用」开关，停用即不参与故障转移；
3. **上移/下移排序**：顺序即故障转移顺序，首行上移与末行下移自动置灰（`opacity-40 + cursor-not-allowed` 视觉禁用）；
4. **自动故障转移**：按序遍历启用端点，任一成功即返回；全部失败按「重试次数（轮）」整轮重试；
5. **可配置重试时长及次数**：普通组「请求超时（秒）+ 重试次数（轮）」，引擎组「行级超时（秒）+ 组级重试次数」；
6. **一键测试**：行级「测试」（按各组真实协议做结构校验，非仅 HTTP 200）与组级「测试全部启用」（模拟故障转移顺序逐条输出）；
7. **行级编辑模式（防误改）**：所有行默认**只读锁定**（地址/超时输入禁用），点击行内「编辑」按钮后方可修改；
   **新增行（_new）的启用开关默认可直接勾选**（无需先进编辑模式），已保存行的开关随编辑态锁定；
   编辑态下显示「保存/取消」按钮——保存即时生效并退出编辑，取消恢复服务端已保存值（未保存的新增行直接移除）；
8. **全局保存 + 恢复默认值**：顶部「保存配置」一键全量落库即时生效；「恢复默认值」经二次确认弹窗后清空配置、业务自动回落内置默认；
9. **占位提示 = 出厂默认值**：输入框 placeholder 即各端点的内置默认地址；
10. **toast 轻提示**：全部操作反馈走顶部居中轻提示浮层，替代原生弹窗。
